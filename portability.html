The Living Specification — Portability

A supporting spec of live-spec.html, which is the entry point and holds the state; this file exists by its split row there (dl-split-portability). It holds the rules under which one collection's content is taken up by another repository: importing, exporting, graduating a supporting spec, and copying a main to start a new project (dl-portability). Read it whole when a move does any of those, or changes the tool's import, export or graduation surface; a session maintaining main does not load it. Decisions establish the required behavior stated here; the tool establishes actual behavior, and where they differ the gap is an open item here (P7).

The routes

Portable content is any subject-shaped knowledge a collection holds: principles, criteria, values, decisions with their reasons, scope boundaries, and deliberately unresolved parameters. Its origin does not limit where it applies. Four routes move it, each with its own continuing relationship (dl-settings, dl-export, dl-graduate, dl-copymain):

  • Import — adopt a subject or component maintained upstream; source, revision, settings and update lineage are recorded.
  • Export — transfer selected subject knowledge once, without restructuring the source; no continuing obligation either way.
  • Graduation — give a supporting spec its own operational life in its own repository; the former parent becomes an importer.
  • Copy a main — start a new project from project-shaped inherited material; the source is provenance, not an upstream.

Preparing material to be carried elsewhere takes no route of its own: author it whole-cloth, or pinch a subject off into a supporting spec (a split row at its parent, P19). A pinched-off spec stays in its collection while other repositories import it; being imported elsewhere never requires graduation. Whole-cloth content need not carry [ADAPT] slots; an extracted spec ordinarily carries actual values, and introducing slots is a deliberate generalization.

Vocabulary

ImportThe relationship between an importer (the adopting repository) and upstream (the repository the content comes from). The imported unit is what is taken (dl-settings).

Version settingPinned: the import stays at its recorded upstream revision until a deliberate upgrade. Tracking: the importer undertakes to follow upstream, with checks at start and explicit updates (dl-tracking).

Describe a relationship by its settings — “the camper imports electrical mirrored, pinned” — never by a verb on the imported thing. Frozen, adapted, forked, owned and editable are not setting names (dl-settings).

One operating main per repository

A repository has exactly one operating main. Importing exists only between repositories: an independently operating collection requires its own repository, with or without a remote. Collection discovery treats everything under imports/ as imported content, never as an operating main (dl-onemain, dl-importdir).

Import

The unit matches the need

The imported unit is one of: a single subject-shaped supporting file; a main whose whole content is the consumed subject (a free-standing rules set, dl-rulesset); or a whole collection integrated as a component. The importer never takes a broader collection to reach one tangled-in part: it waits for upstream to pinch off or graduate the subject. Adoption answers one judgment the tool cannot infer — is the whole imported unit the subject or component you are adopting? — and records it (dl-unit). A navigation link with rel="external" leaves another collection independent and establishes no import.

The receiving split row and the import folder

Each import is justified by a split row at the importer (split row) recording the upstream source, the adopted revision, the edits setting, the version setting and the adoption reason, with the alternatives rejected. The selection cell links exactly one file, the unit's entry file at its imported path; the reason cell carries the record as one visible declaration, <code data-import>SOURCE @ REV mirrored|melded pinned|tracking</code> (dl-importdecl). The recorded revision is the upstream revision the local copy descends from — for a melded import the merge base, not a claim that local bytes equal upstream's (dl-versionrec).

Each import lives in imports/<name>/, the name chosen by the importer and stable across updates, with upstream's internal layout preserved so its relative links resolve without rewriting mirrored bytes. The importer links into imported claims by ordinary paths, imports/electrical/battery.html#capacity. A melded main is demoted at that path; its supporting files keep their positions (dl-importdir).

File selection

The importer names one entry file in an upstream repository at a revision. The unit is that file; everything reachable from it through split rows (P19), upstream's own imports included; and every other file of that repository those spec files link or embed (any href, src or srcset), so mirrored internal links and figures do not break. External URLs are unchanged; everything else stays behind, upstream's tool copy included — the importer carries its own (dl-rule-locality). The tool lists the selection before writing anything (dl-selection). For a melded import this is the starting copy, and the meld commit leaves every link in the melded content resolving in the importer — keep the file, re-point the link, or drop it.

Participation follows the edits setting

Both settings include imported files in the receiving collection for reading and dependency purposes; the importer may link depends-on to any imported claim, an imported main's included, and a changed target owes review. There is no third participation switch (dl-participation).

Operation and claim authority

The importer governs the operation of its collection — commit types, the gate, the entry file, the bootloader, the tooling instruction; an imported main's corresponding declarations have no authority over it, and its status line never becomes the importer's bootloader, though the importer may link it. The content governs what it claims: its decisions, reasons and authority ranking travel with it (dl-operate, P7). A broken link between two mirrored files is FYI; a defect that breaks the importer's own link into the import blocks, a missing depends-on or answering target included.

Demoting a melded main

A main is a file carrying a status line or a commit-type declaration. At melding — at adoption or by a switch from mirrored — remove the imported main's status line, conventions, commit-type declaration and tooling instruction, whatever element holds them; melded content still carrying any of them fails the check; retain its split rows and supporting files, now one hop further down the importer's collection; retain its open items, watches and decision rows as the importer's. A later upstream edit to a removed part surfaces as a merge conflict the tool resolves by dropping that part; every other conflict is resolved by hand (dl-demote). A modified component that must remain a main is a git clone of upstream operated as a repository of its own — its remote is the tracking relationship, its main the one operating main there — and imported from there; a separate route, not a setting (dl-forkroute).

Parameters: slots, answers and overrides

A slot is an id'd element of mirrored content whose own text carries an [ADAPT] marker; a marker outside any id'd element cannot be answered and is upstream's to address (dl-slotmarkup). A mirrored import's slots are answered in the importer's own canonical store, normally its Key Parameters: each answer an ordinary claim with its own status and provenance, carrying rel="resolves" to the slot — a typed edge like depends-on, so an upgrade that changes the slot's text owes review of the answer. The imported file never holds the importer's value. Every slot has one disposition in the importer's own content, and a slot with none blocks the commit (dl-slots, P6):

DispositionRequired content
AnswerA parameter row with an answering link to the slot
Open itemA row id'd open-… linking the slot and stating what resolves it
Does not applyAn answer row and answering link, with the reason it does not apply

Two answers to one slot in one collection's own files block: one value, two homes (P1). Different collections answer the same slot differently, and one collection's dependence on another's answer is an ordinary depends-on link; the tool infers no cross-collection conflict. A melded import's slots are the importer's own [ADAPT]s, filled in place before commit or replaced by an open item — the value itself, or a pointer to a canonical row in the importer's parameters; an upstream rewording of a filled slot is a merge conflict resolved by hand. Changing the edits setting preserves one home per value: mirrored to melded moves answers into the slots or points the slots at parameter rows, and the answering edges retire with the switch, acknowledged by the update item rather than a review; melded to mirrored drops local edits and moves answers out to the parameters table. The tool makes the switch at the recorded revision (lspec import --update NAME --edits … --version …); a row whose declaration changes by any other hand is refused, and any change to a mirrored import's row puts every file of the unit to the test, not only the files that commit stages (dl-importdecl).

An omission is not an override. A mirrored import is taken as written: the importer answers an intentional blank and never overrides a concrete upstream value from its own files, because overriding a fuse rating while mirroring the wire-gauge claims sized for it leaves the importer relying on claims it cannot repair. Departing from a concrete value takes a melded import and a local edit (dl-slots).

When upstream removes or fills an answered slot, the answering link breaks and blocks. The importer disposes of the answer without a broken link or a second home: delete it when upstream settled the fact; re-home the value with new provenance and no answering link when upstream no longer holds a fact the importer still needs; or import melded and edit when it disagrees with upstream's new value. A re-homed value neither restates a value upstream now holds nor contradicts it.

Nested imports and duplicate subjects

A component's own imports arrive inside its tree at the revisions the component reviewed against; only the component updates those relationships, and the outer importer receives a newer nested copy only by taking a newer component. The component's nested slots are the component's to answer: the outer importer depends on that answer and never answers the slot again. A unit the outer importer also imports directly gets its own copy at its own path, identical bytes or not; sharing one copy would mean remapping links inside mirrored content (dl-nested).

lspec import fetches the unit from upstream at a revision, writes ordinary files into the importer's repository, and fills in the split row; the result is staged changes that pass reconcile and one typed commit. No transport operation creates a commit, and upstream's commit history is not imported: the importer's history records each adoption and update with its upstream hash (dl-transport). The blob ids each fetch wrote are kept as transaction state (lspec/imports.json, dl-state): the gate's evidence that a staged change to mirrored bytes, or to the row's revision, came from the tool and not from a hand (dl-importdecl). A mirrored update replaces the files with the new revision's bytes and the split row's hash; a melded update three-way-merges the recorded base, the new revision and the local copy, leaving conflicts for hand resolution except the demoted parts (demotion); a file the importer dropped stays dropped (selection). An update commit passes the gate like any other, and recording a new hash discharges no review it triggers (dl-reviewgit).

lspec start checks each tracking import and reports when it is behind (“electrical: upstream has 3 new commits since abc123”) — a notice, not a block; pinned imports are not checked; an unreachable upstream is reported and start continues; the check never prompts for credentials and gives up on a silent network. lspec import --update <name> fetches, replaces or merges, and leaves the changes staged for the gate (dl-tracking).

Graduation

Graduation changes who runs a subject, not who can use it: a supporting spec graduates when it needs its own status line, open items, watches, sessions, commit vocabulary or maintainer. It moves into a new repository and its existing file is converted into that repository's main by adding the operating parts; wrapping the unchanged subject in an operations-only main is not offered (dl-graduate). The former parent becomes an ordinary importer whose dependency links cross the new boundary.

  1. Choose the destination. The user supplies the new repository's name, directory and remote, if any; the tool asks and never invents them. The recorded source is the remote URL when there is one, else the local path.
  2. Seed the new repository. Build the converted main from the supporting spec as committed in the old parent at a named commit; create fresh history with a seed: commit whose body names the source (graduated from <repo> @ <commit>). Subject-shaped status carries intact (dl-gradproc).
  3. Replace ownership in the old parent. In one commit, remove the old file and split row, import the new main into imports/<name>/ with its split row and settings, and re-point parent-owned links.
  4. Complete review. Targets moved without substantive change take address-only confirmations; the ordinary gate covers the rest.

The old parent keeps its supporting spec until the replacement commit, so there is no gap; its earlier history stays readable there. A source that moves (a local repository gaining a remote) is an address-only change at its importers. A repository holding only a body of rules is one maintained main declared live-system, its substance the rules, decisions, fence and slots — live-spec.html is the precedent; importers take it as a main-shaped unit (dl-rulesset).

One-off export

An export is subject-shaped material selected from a collection that neither reshapes itself nor maintains content for others. No relationship survives: the source records and owes nothing, the recipient cannot track or update from it, and there is no split row or setting. The artifact is an ordinary spec-shaped HTML file holding the relevant parameters, decision rows with their rejected alternatives and reasons, fence items and provenance — each item carrying its source and commit (from <source> @ <commit>) and keeping its status. The exporter selects only material true of the subject, the same judgment as pinching off. It is written outside the source repository, which records nothing. The recipient places it in its own structure, merging into existing files or splitting a supporting spec with an ordinary split row, through the normal gate; later fit changes are ordinary edits to owned content (dl-export).

Copying a main to start a new project

Copying a whole main for a new project is project-shaped inheritance, not an import: the first commit is seed:, starting a new lineage, and the source is history rather than an upstream. A copied main mixes subject knowledge with project-specific facts, so inherited evidence cannot stay confirmed. The rule: demote evidence mechanically, answer judgments one item at a time, regenerate derived views (dl-copymain). The tool resets the status line first, then demotes every evidence token at the seed — the confirmed word of the instance's declared vocabulary, in any case and with any separator — with source and revision provenance (inherited from <spec> @ <commit>), and reports where the word remains as prose; each token is reconfirmed as checked. Inherited rows take individual gate questions answered against their text:

This procedure applies to copied mains only; imports, exports and graduation are subject-shaped transfers whose status travels intact.

The version of live-spec an instance carries

Two records serve two purposes: the receiving split row records the adopted unit's revision and settings; one footer line in the instance main records the upstream revision of the rules and tool it carries, beside attribution and license — github.com/claybford/live-spec @ 2b8c8e2. Clayton Ford, 2026. MIT. The hash is the commit the instance's copy came from; the attribution year is copied as it stands there, in the form dl-yearform fixes. Rules and tool — the seed-derived paragraphs, lspec.py and hooks/ — share one version and upgrade together, the paragraphs brought to that commit's seed text; a graduate carries its parent's line (dl-versionrec, dl-rule-locality).

Where the rules live, and how a session finds them

These rules live here and nowhere an instance carries: the seed does not include them and no rules paragraph is added to an instance main at first import, since every session reads its main whole and the tool states and enforces them (dl-rulehome). For every instance, lspec start and --help point to the verbs' own help — import, export, graduate, copy; while imports exist, start lists their settings and obligations, upstream watches and open items as FYI for mirrored content, unanswered slots and tracking notices, and the gate enforces importer-owned obligations at every commit. A tool-less session sees the settings without their definitions: accepted, since the seed already tells it to perform the tool's checks by hand and the tool ships with the instance.

Out of scope (this file)

Package-manager machinery — version ranges, dependency resolvers, registries, shared-copy deduplication — is out of scope by the main's fence (dl-portability). So is making every subject its own project: moving content never requires upstream to operate the importer's project, nor the importer to operate upstream's. Critiques that an import should be a git subtree or submodule are answered at dl-transport.
