The Living Specification

A document pattern for advancing one technical design across many separate, stateless AI chat sessions: the document, not the conversation, holds the whole state of the work, and each session loads it, advances it, and writes it back. It applies to any solution type (the type mapping) and to either regime — a thing still converging toward done, or one already running and maintained.

Status: live-system, maintained (dl-selfregime) — this document is applied and follows its own pattern; its indexed external artifact is the file's git history (dl-snapshots).
Locked: the four cornerstones / nineteen principles (Cornerstones I–IV), the collection rule among them (P19, dl-unlock); the HTML + water.css substrate; the two-regime framing; git as the sole record (dl-snapshots); one typed edge (dl-dependson).
Open: none in the core; [ADAPT] slots resolve in the reader's instance, not here (dl-noopen).
Top risk: drift-by-accretion — this document out-growing its own compression rules (anti-patterns, dl-twohomes).
Last full sweep: 2026-09-09 — derived from git's latest completed full sweep of this spec (P14).
Read every line of this file before acting on it (dl-wholeload); the seed alone is not the spec. To start a new spec: copy the seed verbatim. To audit one: run the session protocol — with the tool installed, python3 lspec.py start (dl-cli).

What this is: a methodology spec — it teaches the principles, conventions, and structure that let a long-lived design document act as durable project memory for an AI that has none.

Conventions (canonical homes in parentheses): the whole file is the load unit — keep the document short; read it whole (dl-wholeload); when state spans files, one is the main spec and every other file exists only by a split row at its parent (P19). Every value lives in one canonical home, or is an indexed authority pointing at the artifact that holds it (P1, P7). Status tokens: confirmed / provisional / locked / open / watch (P5). Git is the sole record: content changes and audit events are commits, a full sweep an audit: commit, empty only when no files change (dl-snapshots). Each decision-log cell (selection, rejected/replaced, reason) ≤ 40 words (dl-twohomes); each commit is one typed line pointing to rationale, never restating it (P16), with the type from the set declared in docs fix seed audit review tool — main's single declaration governs the collection and the commit-msg hook rejects any other type (dl-committypes). A claim marked data-sealed changes only with a same-commit decision row naming it in data-changes (dl-seal). Session protocol: load the whole file → make one move → write back to the one canonical place → reconcile the touched node's one-hop neighbors → make one commit → confirm nothing remains uncommitted (the session protocol).

The Minimum Viable Version & the Seed

Four devices are load-bearing from day one; missing any one is what causes a multi-session effort to fall apart:

  1. A bootloader line (P14) — a cold session orients instantly.
  2. A canonical store (P1) — values cannot drift.
  3. A status vocabulary with provisional values (P5/P6) — trust is legible and work is not blocked.
  4. A decision log with rejected alternatives (P11) — settled choices stay settled.

Add the scope fence (P12) the first time a session derails into a non-goal, the sweep (P8) the first time a conclusion blocks on one unknown, and the de-drift pass (P2) once restatement creeps in. In the live-system regime, promote the ruled-out register the first time a session re-proposes an eliminated cause, and the diagnostic register the second time a confirmed failure is diagnosed; the seed carries the directive slot from day one — fill it with a real stance the first time a session routes around a problem instead of fixing it. Split into a second file only when a session can write the split row (P19); until then the spec is one file.

The seed — kicking off a new spec

Copy the seed verbatim into a new file. Fill its slots using this methodology; resolve every [ADAPT] choice (validate the template with lspec check --template), then put it under version control — the first commit is typed seed: and starts the lineage. Carry the operating rules needed by the features you use. Before the seed commit, identify claims whose validity depends on another claim remaining true and wire those dependencies with rel="depends-on"; navigation alone earns no edge. Record the assessment in the seed commit body, including the reason if no dependencies qualify. Assess likewise which settled claims deserve data-sealed protection — those whose silent change would corrupt intended state, such as irreversible locks and do-not-revert hardenings — and mark them; there is no minimum count, and the reasoning belongs in the same seed-commit assessment. Do not copy this methodology's explanatory body or decision history. Add optional registers when their triggers arise (regimes).

Canonical Vocabulary

Each term is defined once — here or at an anchored definition site; the rest of the document links to these names rather than re-defining them.

TermDefinition
Living SpecificationThe single durable artifact holding the complete current state of a design across sessions. The unit of continuity.
RegimeForward design (converging an unbuilt thing toward a buildable spec) or live-system / maintenance (operational memory for a deployed thing). Orthogonal to domain (two regimes).
Canonical storeThe one place each value lives. Everything else links to it; nothing restates it.
Indexed authorityIn the live-system regime the store may point at the running artifact that holds a value; the document indexes the state and can go stale, with authority document ← artifact for actual behavior; required behavior retains its approved authority (P1, P7).
Status vocabularyA fixed label set for the epistemic state of every fact and decision. Live-system: an event can demote "confirmed" to watch (P5).
Provisional valueA working value shown so downstream work proceeds, flagged not-yet-verified and linked to the item that closes it. Tokens are per-document; the discipline is not.
ProvenanceThe cited origin attached to a value inline. Temporal caveats live in watch entries, not inline (P6).
Authority hierarchyA ranked ordering of sources declared up front for each claim type; resolved contradictions carry the attribution anatomy (P7).
ParameterizationExpressing a result as a function of an open unknown (a sweep) instead of guessing a number.
Final vs pendingThe split between results independent of open unknowns and results that collapse once a measurement lands.
Gating relationshipAn edge from an unknown to what it blocks — the open list as dependency graph and priority order.
Watch entryAn open-list row for a value under suspicion: what's flagged, the triggering event, the date, what re-verifies it. The flagged location carries only a minimal [WATCH] marker linking here (P5, P9).
TombstoneA section flagged for deletion when a named external trigger fires; pairs with an externally-owned blocker (P9).
Neighborhood checkThe verification that fires on every edit: reconcile the touched node's one-hop edges; follow up only into neighbors the fixes changed.
Count checksumA stated cardinality linked to the one enumeration it counts — a check that detects a silently dropped item when the retained count no longer matches (dl-counts).
Decision logThe document's settled decisions, current-state: each choice with the alternative it beat and the reason. A maintained table, not a record (P11).
Ruled-out-hypotheses registerInvestigated-and-disproven causes, kept apart from the decision log (P17).
Diagnostic registerConfirmed recurring failures, one row each: symptom · tell · fix. Sibling of the ruled-out register — eliminated causes there, confirmed recurring ones here (two regimes).
Scope fenceExplicit non-goals and off-limits critiques, written to pre-empt wrong directions.
Prime directiveOne top-level stance governing how every edit is made — the positive complement to the scope fence (P18).
Main specIn a collection, the one file that is the fixed entry point and first load unit; owns project shape, integration knowledge, and the location and role of its direct supporting specs (P19).
Supporting specA file split off from a parent spec to hold detailed subsystem, topic, or operational state; loaded whole when a move or check crosses into it, one file-hop at a time, never speculatively (P19).

Review eventA review: commit naming the dependent claims confirmed or fixed against a changed target; the only thing that discharges a review obligation (dl-reviewgit).
BootloaderThe short top-of-document orientation; a derived view of the lock / open / risk lists (P14).

The Problem This Solves

A non-trivial design — hardware, software, a process, an agent, a project — is too large for one sitting and returns across many separate conversations, possibly with different models. Keeping the design "in the chat" fails the moment the conversation ends. Treat the document as the program's state and the AI as a stateless function over it: each session loads the state, transforms it, and writes it back. (A live, running design may be indexed rather than contained — the two-regime framing, P1.)

Why multi-session AI is a distinct problem

The editor is a capable, confident collaborator with no memory of the last edit and a strong prior toward generic patterns. Five consequences drive the methodology — stated once here; every later "why" leans on them.

Statelessness. A fresh session carries nothing forward, so the artifact must be sufficient to reconstruct the entire state — not a supplement to memory but the whole of it.

Whole-file load. Every session reads the entire artifact — a session that skips sections plans on false state — so length is a per-session cost and brevity is a first-class property; anchors exist so edits and references land on the right element, not so reading can stop early (dl-wholeload).

Fresh-context pattern-matching. A new session eagerly applies the textbook frame and does not carry the hard-won reasons for not doing those things; unwritten rejections get re-litigated every session. This is the most AI-specific pressure and the reason the decision log and scope fence outweigh their human-doc counterparts.

Drift under rotating editors. A value living in five places will be diverged by five sessions; the only safe number of copies is one.

Confident fabrication. Asked for a number it lacks, a model supplies a plausible one; provisional markers with provenance let a later session tell measured fact from placeholder.

Two regimes: forward design vs. live system

A forward design converges an unbuilt thing toward a buildable spec: the convergence vocabulary (sweeps, final-vs-pending, measure-then-commit, lock the irreversible first) is built around that arc. A live, deployed system you maintain makes the artifact durable operational memory instead. The live-system regime has five regime differences, the source of every live-system extension in this document (plus the regime-neutral additions P18 and P19):

  • The document indexes the state; it does not contain it. The running system is canonical for actual behavior; the document is the rationale layer over it and can go stale — authority runs document ← artifact, and the resolution rule for stale observations is "fix the document"; approved requirements retain their authority (P1, P7).
  • "Confirmed" is not monotonic. The environment moves underneath the design. Demotion is event-triggered: the fact gains a minimal [WATCH] marker; the event, date, and re-verification condition live in a watch entry in the open list (P5, dl-watchreg).
  • Unknowns are often not yours to close. Externally-owned blockers pair a locked workaround with a watch and a tombstone flagged for deletion when the external trigger fires (P9).
  • Settled diagnoses need protecting, not just settled choices. Maintenance is mostly debugging; disproven causes get their own register (P17).
  • Maintenance gains a diagnostic register. Confirmed recurring failures earn a symptom · tell · fix row beside the ruled-out register.

The regime is orthogonal to the domain: any column of the type mapping can be either, and a design crosses from the first regime into the second the day it ships. These regimes organize the work; they do not forbid a forward-design session from demoting an invalidated assumption or recording a recurring prototype failure. Use those operations when their triggering conditions arise.

The Four Cornerstones

Nineteen principles, grouped into four jobs the document must do: a rule and why it holds for an amnesiac editor. Principle numbers are stable anchors, not section-order labels: P17 and P18 are live-system additions placed under Cornerstone III (dl-pnum); P19 is a later addition placed under Cornerstone I (dl-unlock).

Cornerstone I — One canonical state, zero drift

P1 · Single source of truth

Rule: every value lives in exactly one canonical place; everything else links to it. Why: a duplicated fact diverges under a memoryless editor; the only safe number of copies is one. Live-system: the store may be an indexed authority over an external artifact instead of holding the value — the artifact is canonical for actual behavior; fix stale observations in the document. Requirements retain their approved authority (the two-regime framing, P7).

P2 · DRY, enforced as maintenance

Rule: treat restatement as a defect and remove it deliberately — but never merge near-duplicates that encode a real boundary (requested vs. granted, internal vs. wire); state one as a delta of the other (dl-nearcopy). Why: prose copies of canonical values diverge silently; de-drift is real work, not cosmetics.

P3 · Addressability & navigation

Rule: give every claim a stable anchor, link densely, provide a TOC; declared counterparts (siblings, pairs) link both ways (dl-bilink). Dependency source and target anchors enclose complete claims (markup contract). Why: a reference is only useful if it can be followed, and an edit must land on the right element.

P4 · Self-documenting conventions

Rule: write the document's editing rules inside the document. Make structural conditions objective and mechanically checkable. Where judgment is required, specify the trigger, what must be inspected, and how to finish: confirm, correct, or post an open item with a resolution condition. Why: the next editor is a fresh model; vague obligations are applied differently every session and decay. Explicit conditions and procedures make the work repeatable (dl-gate).

P19 · A justified collection (regime-neutral)

Rule: the canonical state may span more than one file. When it does, exactly one file is the main spec and fixed entry point; every other file's existence is justified by a split row at the file that split it off, never at itself; the managed collection is exactly the set reachable from main through those rows. Main is loaded first and whole; a supporting spec is loaded whole when a move or check crosses into it, one file-hop at a time, never speculatively (dl-collection). dl-wholeload applies per file: the collection changes what a load is, not that loads are whole. Each supporting spec has exactly one parent, so the collection is a tree; most specs never earn a second file, and a split is a decision against that default (P12). Why: a cold session needs one place to start however many files exist, and a file with no named reason to exist is indistinguishable from an accident — the split row makes "why does this file exist" answerable the way the decision log makes "why this choice" answerable (P1, one level up).

Cornerstone II — Uncertainty is first-class and workable

P5 · A fixed status vocabulary

Rule: label every fact and decision from a small closed set (e.g. confirmed / provisional / locked / open). Why: without explicit status a session over-trusts placeholders or re-opens settled choices. Live-system: "confirmed" is not terminal — an event demotes it to watch; the inline marker stays minimal and the metadata lives in the watch entry (two regimes).

P6 · Provisional-but-actionable, with provenance

Rule: never leave a needed unknown implicit — either a flagged working value with provenance, cited inline and linked to the item that closes it, or mark it open with what would close it. Why: a blank blocks downstream work; a silent guess corrupts it; provenance lets a later session judge and replace.

P7 · Authority hierarchy & honest inconsistency

Rule: declare a ranked authority order up front, scoped by claim type: observed or executable artifacts establish actual behavior; approved requirements and decisions establish required behavior; verification evidence establishes whether behavior meets requirements. Surface known contradictions rather than hide them: both readings, each source, the resolution rule invoked, and the resultant value (dl-contradict). If unresolved, post an open item stating what resolves it. Why: an explicit hierarchy directs correction to the right place; implementation defects do not authorize weakening requirements.

P8 · Parameterize over unknowns; split final from pending

Rule: compute gated results as functions of the open measurement (sweeps) and mark which results are already final. Why: honest progress before unknowns close; the sweep collapses to a number the moment the measurement lands. Live-system siblings: ship a workaround now with a watch and tombstone when the unknown is externally owned (P9); build a structural mitigation — an engineered guard, not a predicted number — where a value cannot be made final.

P9 · The open list is a dependency graph

Rule: record what each open item gates; order action by it; take no irreversible step before the measurement that governs it. Why: ungated, the open list is worked in arbitrary order — and an irreversible step taken before its governing measurement is the one error no later session can undo. Live-system: externally-owned blockers resolve on a third party's action — pair each with a locked workaround, a watch, and a tombstone; a workaround kept post-fix because it is more robust is a legal resolution.

Cornerstone III — Settled decisions are protected

P10 · Layered commitment

Rule: lock the irreversible structural decisions first and say so; let detail layers stay fluid beneath the lock. When a lock depends on an assumption, record that assumption and the condition that reopens the decision, in the rationale or a linked canonical claim. Why: re-opening the foundation is the most expensive thing a framework-hungry fresh session can do.

P11 · Decision log — choice, rejected alternative, reason

Rule: log each decision with the alternative it beat and the reason. Keep the log current-state: a superseded row is removed, its position surviving in the successor's rejected/replaced cell; the transition belongs to git (dl-current, P16). Why: the log answers a re-proposed alternative before it is argued, and makes reversal deliberate.

P12 · Scope fence / non-goals

Rule: state what is out of scope and which critiques do not apply. Why: converts a recurring derailment into a one-time statement; negative prompting for the design.

P13 · Partition proven from novel; lead with risk

Rule: separate reused/proven subsystems from the genuinely new work; name the single biggest open risk up front; cite existence-proofs honestly ("someone did something like this" is not "this is done"). Why: attention concentrates where the danger is, and not on the proven layer.

P17 · A ruled-out-hypotheses register (live-system)

Rule: keep a register of investigated-and-disproven causes, separate from the decision log: what was tested, what ruled it out, where the real cause lives. Its sibling is the diagnostic register — confirmed recurring failures, one symptom · tell · fix row each. Why: a disproven diagnosis has no chosen counterpart, so the decision log cannot hold it — and fresh sessions re-propose it exactly as they re-propose rejected alternatives.

P18 · A prime directive — positive prompting (live-system origin; regime-neutral)

Rule: state, once and at the top, the single stance that governs how every edit is made — the positive complement to the scope fence. Why: pre-empts the strongest fresh-model default, the local shim that routes around a problem instead of resolving it.

Cornerstone IV — Reconstructable and auditable

P14 · A bootloader line

Rule: open with a few sentences giving lifecycle stage, what is locked, what remains, and the top risk — present-tense state only. Change notes and derivation narrative live in git and the decision log, never up top (dl-nohist); the tense tell decides placement: state is present-tense, history is past-tense. The bootloader is a derived view — the one sanctioned restatement: when reporting recorded state, attribute it to the spec; regenerate it whole from its named canonical sources on each pass; a clause with no source is promoted or deleted, and a contradiction with its sources is surfaced (dl-bootloader). Why: a cold session orients in one paragraph instead of re-deriving "where are we."

P15 · Show the reasoning and the tooling

Rule: include the governing logic (equations, contracts, rules) and point to the executable model, not just conclusions. Why: a session that can see how a number was produced recomputes instead of trusting a stale figure.

P16 · Typed, disciplined commit messages

Rule: every session-event is a git commit — the boundary rule, stated once, is every session-event is a commit; a clean sweep may update bookkeeping; its commit is empty when no files change. Gate on the objective binary — did something happen this session (is there a commit, empty or not) — and type each message from a small closed set: a content change is a normal commit typed from that set; a defect-fixing sweep is a normal commit typed audit:; a clean full sweep takes an audit: commit, empty only when no files change (git commit --allow-empty); a recorded review is a commit typed review: naming the dependent claims it clears, empty when the claim needed no edit (dl-reviewgit); a review's or seed commit's subject stays one typed line, and its body may carry the assessment — evidence lives in git (dl-recordgit). Each message is one typed line recording the transition and pointing to rationale, never restating it (dl-snapshots). Why: the trail stays complete under rotating editors, and rationale duplicated into a commit is a stale copy.

The Session Protocol

The cornerstones describe the static artifact; this loop operates it. A fresh session can be told simply: "follow the session protocol."

  1. Load. Read the whole document — it is the load unit (dl-wholeload). Orientation priority: the bootloader, the canonical store, the open list, the decision log, the scope fence; in the live-system regime also the prime directive and the bootloader's last-sweep line; before proposing causes in debugging work, the ruled-out and diagnostic registers. In a collection, main first and whole; a supporting spec is loaded whole when a move or check crosses into it, one file-hop at a time (P19). Whole means every line of every file loaded, end to end: no ranged views, no search in place of reading, no summary standing in for the text. A session that has not done this has not loaded the spec and may not edit it (dl-wholeload). If an instruction refers to a prior proposal, decision, or wording you cannot locate in the available conversation, document, or git history, report it as not found. State any interpretation before acting; ask for clarification when competing interpretations would materially change the edit.
  2. Advance — one legal move:
    • Close an unknown: replace a provisional value with a measured one, re-bucket its status, collapse any sweep it gated (P6, P5, P8).
    • Make a decision: move an item from open to locked; write the rejected alternative and reason into the log (P11).
    • Recompute: re-run the logic/model when an input changed; never hand-edit a derived figure (P15).
    • Extend scope: add structure, then immediately fence what it does not cover (P12).
    • De-drift / audit: collapse restatements to pointers (P2); re-derive the bootloader and every roll-up whole (P14); run the grep-shaped checks — the structural subset (e.g. anchor resolution, duplicate ids, count checksums, over-cap cells) is executed by lspec check, run by the pre-commit hook, a red result blocking the commit; semantic obligations (same-fact judgments, retention, evidence support, suspicion scope, and narrative placement) require review with a confirmed, corrected, or explicitly unresolved disposition (dl-twohomes, dl-validator). An audit pass removes or relocates in the core; it never elaborates.
    • Split: create a supporting spec, write the split row at the parent, move the content, reconcile both files. A decision, never a tool action; a file that no longer earns its row is merged back (P19).
    • Review: re-read a dependent claim against its changed target; fix it or confirm it, then commit typed review: naming the dependent claims, empty when nothing changed (dl-reviewgit).
    • Flag an event: when the world under the document moves and you witnessed it, place minimal [WATCH] markers on what the event puts in question and file the watch entries (event, date, re-verifies-when) in the open list. Confirmed recurring diagnoses go to the diagnostic register; any unresolved work remains in the open list and links to the relevant diagnostic row. When fallout can be listed, use flags; otherwise record unenumerable suspicion and follow the sweep rule (dl-sweeptrigger).
    • Full sweep: reconcile the whole document against itself and any indexed ground truth; commit it — an audit: commit, empty only when no files change. It is owed only on unenumerable suspicion — when what-might-be-wrong cannot be listed, the only honest scope is everything: (a) a defect of a neighborhood-check edge type found where no recent edit touched — evidence a past session's check silently failed; (b) an edit that landed out-of-band of the protocol; (c) live-system, advisory at Load: an unwitnessed period past the horizon, if the instance sets one. If the sweep cannot run in the session that incurred it, post a sweep-owed entry to the open list (what was found, what it gates, resolves when a sweep lands as an audit: commit). Enumerable suspicion never obliges a sweep; the triggers say when one is owed, not when one is permitted — an elective sweep is always legal and takes an audit: commit (dl-sweeptrigger).

    • inbound — every referrer still holds;
    • outbound — cited rows still say what it assumes; gated items exist; every linked anchor resolves;
    • copies — no stale restatement survives;
    • counterparts — declared sibling/pair relationships still link in both directions (dl-bilink);
    • counts — every count checksum over a set the edit changed still matches (dl-counts);
    • status — the node's own tag is still right;
    • dependents (collection) — every claim linking here with rel="depends-on" owes review when this node's rendered text changed; an address-only change (id moved, content identical) is reported apart and confirmed cheaply. Source and target ids enclose complete claims (P3). The dependent claim is the link's nearest ancestor with an id; a link whose source id differs from the basis commit is reported like an address-only change, since restructuring can move an obligation without breaking a reference — by hand, any edit restructuring the paragraph around a depends-on link is treated the same way; plain links carry no obligation. If review history is unavailable, fetch it or re-review the claim against committed state and record the review in git. No review ledger or history narrative in the spec (dl-dependson).
    • indexed artifact (live-system) — it still matches the external artifact it indexes; apply the declared authority hierarchy (P7).
    A neighbor changed by the fixes owes the same check; a neighbor verified unchanged ends the follow-up. Finish with one commit — a sweep takes an audit: commit, empty only when no files change (P16) — then run the completion check: lspec check --clean reports anything staged, unstaged, or untracked repo-wide and fails while any remain; it detects outstanding changes when invoked and neither forces its own invocation nor proves a clean audit was recorded (dl-clean). The artifact is the new state; discard the conversation.

With lspec installed (dl-cli): start MAIN at Load delivers main whole, builds the derived graph, and lists owed reviews and every verb; show FILE (or start --with FILE) delivers a supporting spec whole, and any output that crosses into another file names that command; check --diff HEAD and neighbors run the edge list above; mv renames with reference repair; review records the event; check --clean is the completion check after committing; show and impact are elective and met in start's listing; the hooks run check --staged — pre-commit for structure and the seal gate, commit-msg for the review and vocabulary gates — and block red (dl-hook). Every result is stamped with the commit it was computed against (dl-concurrency). Absent the tool, each step is done by hand.

Verification is reference-following: it catches only defects that break a reference. A drift class that breaks none gets a rule that wires one — retained counts for cardinality mismatches, git history for lossy moves and retrojected entries, whole-view re-derivation for fossil clauses (dl-counts, dl-snapshots, dl-bootloader).

The discipline: changes are surgical and logged, the canonical store is touched in exactly one place, every touched node's neighborhood is reconciled, and rationale is preserved rather than re-derived.

The pattern also has recognized kin in the specification literature itself: its live-system regime is the in-service / maintained-as specification, and its executable, always-current character is Specification by Example's "Living Documentation" reached from the stateless-editor side. The regime is orthogonal to every column: a scoped project is the forward regime, a continuous program is the live-system regime, and the maintenance regime adds the five differences of the two-regime framing to whichever column applies.

Substrate Notes — the format is load-bearing, not packaging

Granular addressability. HTML gives arbitrary id anchors on any element — table rows, spans, list items — which is what the dense reference web (P3) runs on. Markdown anchors only headings natively; the swap quietly discards a property the method depends on.

One file per spec, renders identically anywhere. A collection is several such files, each whole (P19). The artifact passes between humans and stateless sessions with no tooling and navigation intact. "Self-contained" scopes to the state; presentation is externalized to one stylesheet dependency and degrades gracefully to plain semantic HTML offline (dl-substrate).

Git is the memory of the memory. A living spec lives in version control: git is the sole record of the document's own past (dl-snapshots), so every content change, audit event (a clean sweep empty only when no files change), and verbatim claim is checkable rather than asserted.

Structural conventions are executable. Decision rows use <tr id="dl-…">; every cell is subject to the cap. The structural checks (P4) — e.g. anchors resolve, no duplicate ids, count checksums, cells within cap — run as lspec check (standard library, no browser), which the pre-commit hook runs on every commit; the artifact stays tooling-free to read, the tool being optional maintenance automation like git, not part of the state (dl-validator). Hooks do not clone with a repo, so CI runs the same check (dl-hook). The embedded seed is checked as a specimen. A dependency anchor encloses its complete claim; a heading alone covers only the title (P3). A count checksum is declared on its enumeration: data-count="differences" on a list, data-count="p=principles" for an id series. A §N that cites an outside document sits inside its link or <cite>; bare, it is read as this collection's own volatile ordinal. Unresolved [ADAPT]/[PROJECT] markers fail instance readiness: check --template validates a template instead, and data-literal on a <code> declares a mention — a declaration the checker trusts, not proof the text is nonoperative. A seed: commit subject types a deliberate initialization or replacement of an instance's lineage, scoped to the files the commit touches; a body line can never type a commit. The commit vocabulary is declared once, in main's conventions, as the text of a single data-commit-types code element — whitespace-separated types, with seed, audit, and review reserved because the tool assigns them operational meanings; the commit-msg hook rejects a subject typed outside the declared set, and a document with no declaration is reported as unenforced, never silently defaulted (dl-committypes). An element with a stable id and the data-sealed attribute is a protected claim: once committed, its normalized text, id, path, marker, and collection membership change only when the same commit adds or substantively updates a decision row whose data-changes attribute names the old repository-relative path#id, whitespace-separated when several — historical identifiers resolved against the comparison baseline, not hyperlinks, so a deleted claim leaves no broken anchor (dl-seal). The gate requires a recorded decision, not proof the decision is sound, and protects marked claims only.

A collection addresses across files. A cross-file reference is path#id; a link to a file outside the collection carries rel="external", any other linked HTML file needs a split row; the graph over a collection is derived from the current files and thrown away, never stored; main is named once per session as the argument to start (dl-graphderived).

Classless CSS is Cornerstone I applied to styling. water.css externalizes presentation to one line, so every session spends its attention on content rather than a bespoke stylesheet it must read, preserve, and avoid breaking. This page ships only the water.css link — no custom block — the same principle taken to its limit, matching the seed.

Net: the principles say what state to hold; the substrate is part of how to hold it. Changing the carrier "for convenience" is a content decision in disguise.

Out of scope (this document)

Tooling specifics (which editor, which AI client, retrieval chunking) and team-collaboration mechanics (locking, concurrent-edit merging) are out of scope — this is the document pattern, not a workflow product; git is the concurrency mechanism assumed (dl-concurrency), and the companion tool is maintenance automation, not a product (dl-cli). Critiques premised on "just use a database / issue tracker / project-management tool" miss the point: the value is a single human- and AI-legible artifact that is the design's state. Nor does the document argue for or evidence its own adoption: its remit is to teach and operate the pattern — seed a new spec, audit an existing one — not to justify it.
